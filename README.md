# Finance Natural-Language-to-SQL

Ask a finance question in plain English. Get back SQL, a plain-English
explanation of what that SQL does, and the rows it returns — after a human
has checked the SQL first.

## What it is, in plain words

Imagine a finance teammate asks, "How much did each department spend?"
instead of writing a database query. This tool takes that plain-English
question, turns it into a database query (SQL), shows the SQL and explains
it in plain English, waits for a human to say "yes, run it", and only then
runs it and shows the results.

It is a learning project built for a Finance Transformation context. It is
**not** a production finance system and it must never be pointed at real
finance data without a proper access and security review.

## Important: no real LLM is called

SQL is generated by **deterministic rules and templates** in `main.py`
(the `translate_question` function). There is no large language model
involved, no API key is needed, and no network request is made. Every
supported question shape maps to one fixed, reviewed SQL template, so the
output is fully explainable and auditable.

There is a documented, pluggable LLM interface in `main.py`
(`LLMTranslatorInterface`) showing exactly where a real LLM API — for
example Snowflake Cortex, or another approved provider — would plug in
later. It is not implemented and it is never called by default. Any LLM
plugged in there would still go through the same validation and the same
human confirmation step. Do not describe this tool as "AI-powered SQL
generation" unless that interface has actually been implemented and
approved.

## How it works

1. **Ask** — type a question, or pass it with `--question`.
2. **Translate** — deterministic templates turn the question into one SQL
   `SELECT` statement, plus a plain-English explanation.
3. **Validate** — the SQL is checked before it runs:
   - it must be a read-only `SELECT` (one statement only);
   - it must not contain any write keyword (`DELETE`, `UPDATE`, `DROP`,
     `INSERT`, `ALTER`, `TRUNCATE`, `CREATE`, `GRANT`, `REVOKE`, ...);
   - every table it uses must be in the known schema;
   - any vendor or department name in it must exist in the database.
   Questions asking for a write, or about a table/column that does not
   exist (for example payroll or employee salary), are **rejected** and
   nothing runs.
4. **Human check** — the SQL and its explanation are shown, and a human
   must type `y` before anything runs. This is the human-in-the-loop
   checkpoint. `--auto-confirm` skips it and is only for the automated
   eval run, never the normal way to run a finance query.
5. **Run and show** — the query runs against a local SQLite database and
   prints the SQL, the explanation, and the rows.

## The data (synthetic)

All data is **synthetic and invented** for learning. It describes no real
company, vendor, person, or transaction. Amounts, names, and totals are
made-up example numbers, clearly labelled synthetic.

Four tables, built from the CSVs in `data/` by `data/build_db.py`:

| Table | Rows | What it holds |
| --- | --- | --- |
| `departments` | 10 | Department name, cost centre, budget owner, annual budget |
| `vendors` | 12 | Vendor name, type, country, active flag |
| `transactions` | 40 | Date, vendor, department, category, description, amount, currency, status, payment method |
| `monthly_close` | 12 | Close month, department, total spend, transaction count, close status |

The monthly-close totals are illustrative example numbers; they are not
reconciled to the transactions table. The database file (`data/finance.db`)
is generated locally and is ignored by `.gitignore` — rebuild it any time
with `python3 data/build_db.py`.

## How to run

Requirements: Python 3 (standard library only — no packages to install,
no API key, no paid service).

```bash
cd finance-natural-language-to-sql

# See example questions
python3 main.py --list-examples

# Ask a question (you will be asked to confirm before it runs)
python3 main.py "total spend by department"

# Or answer the interactive prompt
python3 main.py

# Save the SQL, explanation and rows to a file as well
python3 main.py --question "top 5 vendors by spend" --output output/result.txt

# Run the eval set (auto-confirm is used here only)
python3 main.py --eval
```

Example questions that work:

- `total spend by department`
- `top 5 vendors by spend`
- `transactions over $1000`
- `count transactions by status`
- `total spend for Northwind Cloud Services`
- `average transaction amount by category`
- `monthly close totals for September 2026`
- `list transactions for the Engineering department`
- `total spend by category`
- `show flagged transactions`
- `total spend in September 2026`

Questions that are rejected on purpose:

- `Delete all transactions from the database` — rejected as unsafe
- `Drop the transactions table` — rejected as unsafe
- `Show total salary paid to each employee` — rejected: no payroll or
  employee table exists in this schema

## Eval and pass bar

The eval set (`evals/eval-set.csv`) has 14 cases: 11 valid questions, 2
that must be rejected as unsafe/non-read-only, and 1 about a table/column
that does not exist.

**Pass bar for a valid question:** the generated SQL must match the
expected SQL exactly, pass validation, run without error, and satisfy the
rubric's row check (for example, the right row count, or counts that add
up to the 40 transactions in the data).

**Pass bar for a rejected question:** the question must be rejected with
the expected reason and nothing may run.

Run it with `python3 main.py --eval`. The results recorded in
`evals/eval-set.csv` (and `evals/eval-results.csv`) are the true results
of the last run — a failed test is recorded as failed, never edited to
look like a pass. The pass bar for the whole set is **14/14**.

## Risks and guardrails

- **Wrong SQL, wrong numbers.** A template can misunderstand a question
  (for example, which month or vendor was meant). Guardrail: the SQL and
  a plain-English explanation are always shown, and a human must confirm
  before anything runs.
- **Unsafe operations.** A user could ask to delete or change data.
  Guardrail: only `SELECT` is generated or allowed; write keywords are
  rejected at translation time and again at validation time.
- **Asking about data that is not there.** Guardrail: unknown tables and
  columns are rejected instead of guessed at.
- **No real LLM is involved.** The deterministic templates only cover the
  question shapes listed above. Anything else is rejected as unsupported
  rather than answered with a made-up query.
- **Synthetic data only.** The database holds invented numbers. Nothing
  here is a real financial record, and the tool must not be connected to
  real finance systems without access control, audit logging, and review.
- **No audit log yet.** Runs print to the screen and can be saved with
  `--output`, but there is no permanent audit trail of who ran what. That
  would be required before any real use.

## Human-in-the-loop

The human confirmation step is not optional decoration: it is the control
that makes this safe to use in a Finance setting. The default is to ask
every time. `--auto-confirm` exists only so the eval script can run
without a person at the keyboard, and it must not become the normal way
to run queries.

## Staged release note

- **Stage 1 (this project):** local only, synthetic data, deterministic
  templates, human confirmation on every run.
- **Stage 2 (next):** add an audit log of every question, SQL, decision,
  and result; add more question shapes only after adding eval cases for
  them first.
- **Stage 3 (later, only with approval):** plug a real, approved LLM into
  `LLMTranslatorInterface` behind the same validation and human check,
  and only then evaluate it against this same eval set — the deterministic
  results are the baseline it has to beat.
- **Not in scope:** connecting to real finance data, production use, or
  removing the human confirmation step.
